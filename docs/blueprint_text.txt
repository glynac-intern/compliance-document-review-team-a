Big Whole Architecture 1.1 Objective The Compliance Document Review App provides a controlled workflow through which financial advisors submit client-facing documents for compliance review. The system must support: Advisor and Compliance Officer authentication. Secure document submission. PDF, DOCX and XLSX files up to 10 MB. Compliance review queue. AI-assisted document summarisation. AI-assisted compliance issue detection. Vector-based rule retrieval. Missing-disclosure detection. Similar precedent retrieval. Human compliance decisions. Revision/resubmission workflow. Full audit history. Graceful operation when AI services are unavailable. The AI provides assistance only. The Compliance Officer remains responsible for the final decision. 1.2 High-Level Architecture ┌───────────────────────────────────────────────────────────┐ │                        FRONTEND Architectural Principles Human-in-the-Loop AI assists the reviewer but never determines document status. Privacy Before AI PII must be removed before document text reaches either an external LLM or hosted embedding service. Retrieval Before Generation Relevant rules/disclosures/precedents are retrieved before asking the model to analyse compliance issues. Traceability Every compliance flag must identify: Triggering passage. Retrieved rule. Explanation. Graceful Degradation Failure of an external AI service must not stop the Compliance Officer from reviewing or deciding a document. Reproducibility A developer outside Team A must be able to clone the repository, follow the README and run the application and tests. 2. AI Design 4.1 Responsibilities AI track owns: Server-side PII masking. Summary generation. Compliance flag generation. Flag explanations. AI response validation. Integration with retrieved context. Analysis retry behavior. 4.2 PII Masking Before any external AI call: Original Text       ↓ PII Detection       ↓ Stable Placeholder Replacement       ↓ Masked Text       ↓ External Service Examples: John Smith -> [CLIENT_1] john@example.com -> [EMAIL_1] 123456789 -> [ACCOUNT_1] Mapping remains server-side. 4.3 AI Analysis Inputs may include: Masked document text. Relevant retrieved compliance rules. Missing-disclosure evidence. Relevant document context. Outputs: summary flags[] Each flag contains: passage matched_rule reason severity 4.4 AI Decision Boundary AI must never: Approve. Reject. Set Needs Revision. Automatically modify document status. Only a Compliance Officer records the decision. 4.5 Caching AI analysis is cached per document. Analysis should not rerun on every page load. Retry is permitted after analysis failure. 5. Decisions: Decision Status Embedding provider TBD Embedding model TBD Vector dimension TBD Similarity metric TBD Batch size TBD 5.7 Retrieval Job 1 — Rule Retrieval Document Chunk       ↓ Embedding       ↓ Vector Similarity Search       ↓ Relevant Compliance Rules       ↓ AI Compliance Check The goal is to retrieve rules relevant to the actual passage rather than asking a general model whether the entire document is compliant. 5.8 Retrieval Job 2 — Missing Disclosure Detection Approved disclosure texts are embedded. For each required disclosure: Required Disclosure         ↓ Vector Similarity         ↓ Search Document Chunks         ↓ Best Similarity Score         ↓ Above threshold? ─ Yes -> Present         │         No         ↓ Potential Missing Disclosure The presence/missing threshold must be tuned experimentally. 5.9 Retrieval Job 3 — Precedent Search Reviewed documents are indexed with: Masked document content. Officer decision. Officer comment. For a new submission: New Document       ↓ Similarity Search       ↓ Top 3 Reviewed Documents       ↓ Previous Decision + Comment The specification fixes the precedent result count at   three . 5.10 Retrieval Evaluation Data Engineering should record experiments involving: Chunk size. Overlap. Embedding model. Similarity metric. Top-K. Disclosure threshold. Suggested evaluation questions: Does the correct rule appear in retrieved results? Are irrelevant rules dominating results? Are paraphrased disclosures correctly recognised? Are genuinely missing disclosures detected? Are precedent documents semantically relevant? 6. Risks, Dependencies & Blockers Risk: Cross-Track Dependency Delays Example: Upload → Extraction → Masking → Embedding → Retrieval → AI → UI A delay at one boundary can block downstream work. Mitigation Agree interfaces early. Use mock data/responses. Track blockers daily. Reassign abandoned critical initiatives when necessary. Risk: PII Leakage Mitigation: Mask before external calls. Automated tests. Inspect outbound payloads. Risk: Poor Retrieval Mitigation: Experiment with: Chunk size. Overlap. Embedding model. Similarity metric. Thresholds. Risk: AI Provider Limits Mitigation: Cache results. Retry. Graceful degradation. Avoid unnecessary calls. Risk: Over-Engineering Mitigation: Prioritise the assessment requirements over sophisticated architecture or stretch features. Risk: Integration Only Happens at the End Mitigation: Use the   4 Sep, 11 Sep and 18 Sep integration checkpoints   defined in the timeline. 21. Definition of Done / Acceptance Criteria The project is complete when: Advisor can sign up. Officer can sign up. Advisor can upload PDF/DOCX/XLSX. Officer sees submission in filterable queue. Officer can open document. AI summary is displayed when available. AI flags are displayed. Each flag contains passage + rule + explanation. Officer can approve/reject/request revision. Advisor sees decision and comment. Revision remains linked to original. Audit history records actors/actions/timestamps. Both role boundaries are enforced at API level. PII is masked before LLM calls. PII is masked before embedding calls. Three relevant precedents can be retrieved. AI failure does not block review. Tests pass. Clean checkout works.
